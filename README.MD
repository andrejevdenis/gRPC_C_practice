# Архитектура, ООП-проектирование и Хаос-тестирование gRPC микросервисов на C++

Репозиторий представляет собой законченный коммерческий кейс (Case Study) по развертыванию, ООП-изоляции, профилированию памяти и стресс-тестированию высокопроизводительных микросервисов на базе **gRPC** и **Protocol Buffers** в среде Windows и Linux (WSL).

---

## 🛠️ Архитектура окружения и эволюция инструментов

В ходе проектирования тестовой инфраструктуры был пройден путь от ручной сборки бинарных контрактов до автоматизированных Linux-контуров:
1. **Эмуляция внешних зависимостей (Mocking)**: Первоначальные тесты gRPC-заглушек были развернуты внутри изолированного Linux-контура **Ubuntu (WSL)** с использованием контейнеризированного движка **GripMock**. Это позволило осуществлять динамический маппинг (`stub.json`) без необходимости генерации бинарных дескрипторов `.dsc`.
2. **Валидация через Postman**: Было успешно протестировано бинарное сетевое gRPC-взаимодействие между хостовой ОС Windows (Postman gRPC Client) и изолированной подсистемой WSL (`localhost:4770`).
3. **Исключение избыточных артефактов**: На этапе оптимизации репозиторий полностью очищен от локальных утилит компиляции (`protoc.exe`) и промежуточных дескрипторов. Кодогенерация C++ классов полностью автоматизирована через инкрементальные команды `add_custom_command` внутри `CMakeLists.txt` самого проекта Visual Studio.

## 📂 ООП-Структура C++ репозитория (Clean Architecture)

Проект автотестов на C++ спроектирован в соответствии с принципами разделения ответственности и паттерном, аналогичным *Page Object* в веб-тестировании. Инфраструктура полностью отделена от тест-кейсов.

*   `proto/` — Единый источник правды. Содержит файл gRPC-контракта `service.proto`.
*   `include/` — Слой переиспользуемых ООП-компонентов:
    *   `fake_user_server.h` — Оболочка управления изолированным gRPC-сервером (`In-Process`). Берет на себя автоматический запуск (`BuildAndStart`) и безопасную остановку (`Shutdown`).
    *   `user_grpc_client.h` — Высокоуровневый клиент-фасад. Инкапсулирует работу с `ClientContext`, каналами связи и генерацией `Stub`. Предоставляет тестам чистые C++ методы вроде `GetUserProfile(name)`.
*   `tests/` — Слой чистых тест-кейсов (**Google Test** фреймворк). Содержит файлы шагов и валидации, полностью избавленные от рутинного кода инициализации сети.

## 📈 Результаты нагрузочного тестирования (RPS Benchmark)

Тестирование производительности и многопоточного масштабирования проводилось на серверном процессоре **Intel Xeon X5675** (6 физических ядер / 12 логических потоков) в режиме `In-Process Channel` на объеме в **10 000 gRPC-запросов**.

### 1. Вертикальное масштабирование (Закон Амдала на практике)
*   **1 поток**: Обработка заняла **14 132 мс**, выдав чистую скорость в **708 req/sec**.
*   **4 потока**: Время сократилось до **4 794 мс** (**2 086 req/sec**). Прирост скорости составил **~3.0х** 🚀 за счет параллельной сериализации Protobuf физическими ядрами.
*   **12 потоков**: Время составило **4 162 мс** (**2 402 req/sec**). Рост замедлился из-за конкуренции потоков за ресурсы (Lock Contention) и деления вычислительных блоков технологией Hyper-Threading.

### 2. Сравнение конфигураций сборки (MSVC Compiler)
*   **Release Configuration**: **2 514 req/sec** — максимальная оптимизация кода компилятором (`/O2`), разворачивание циклов, инлайнинг функций.
*   **Debug Configuration**: **1 592 req/sec** — падение производительности в **1.6 раза** из-за отключения оптимизации, включения тяжелых проверок отладочной кучи (Debug Heap) и итераторов STL.

## 🧠 Профилирование оперативной памяти и аудит утечек

Для предотвращения деградации памяти (Memory Leaks) в C++ микросервисах внедрен механизм дифференциального аудита кучи с использованием системных средств Microsoft C-Runtime (`<crtdbg.h>`):
*   Использованы функции `_CrtMemCheckpoint` и `_CrtMemDifference` для взвешивания аллокаций строго в границах выполнения бизнес-логики.
*   Инфраструктура тестов переведена на **Умные указатели (`std::shared_ptr` / `std::unique_ptr`)** и деструкторы, что гарантирует автоматическое освобождение памяти gRPC-каналов.
*   **Архитектурный инсайт**: При первом вызове библиотека Google Protobuf умышленно удерживает в глобальном кэше порядка **35 КБ** (`DescriptorPool`, внутренние бинарные буферы по 399 байт) для оптимизации скорости повторных запросов (Memory Pooling), что подтверждено профилированием.

## 🔴 Хаос-тестирование таймаутов и системный анализ ОС

Для проверки отказоустойчивости в условиях нестабильной сети разработан изолированный `grpc_soak_tests`, моделирующий случайные задержки ответов сервера (**Network Jitter**) в диапазоне от **300 до 700 мс** при жестком дедлайне клиента в **500 мс**. 

В ходе 50 итераций стресс-теста были зафиксированы и задокументированы фундаментальные особенности работы операционных систем:

### 1. Квант времени планировщика Windows (Scheduler Quantum)
При стандартных настройках Windows десктопный планировщик проверяет дедлайны таймеров раз в **~15.6 мс** (частота системных часов 64 Гц). Из-за этого лага gRPC-клиент закрывал зависшие соединения не в 500 мс, а на отметке **514–515 мс**. 

### 2. Активация высокоточного режима ядра Windows API
Для устранения 15-миллисекундного дрейфа внутрь ООП-компонента `FakeUserServer` были интегрированы низкоуровневые вызовы Windows API: `timeBeginPeriod(1)` при инициализации и `timeEndPeriod(1)` в деструкторе. 
*   Это принудительно перевело квант времени ядра Windows на частоту **1 мс**.
*   Погрешность отсечки таймаута сократилась до рекордных **2–4 мс** (**502–504 мс** до полного `ABORTED`), что компенсирует оверхед на переключение контекста потоков (Context Switch).

### 3. Эффект «Гонки дедлайна» (Deadline Grace Period)
В ходе хаос-теста задокументировано явление, актуальное для сетевого продакшена: если поток сервера просыпается ровно в момент дедлайна (500 мс) и успевает протолкнуть бинарный пакет в канал до того, как системный таймер прерывания ОС успеет физически уничтожить контекст на стороне клиента, gRPC-движок закрывает итерацию со статусом **`SUCCESS` на 514-й миллисекунде**, защищая систему от ложных абортов связи.

### 4. Кроссплатформенный стандарт (Linux Enterprise)
Код сервера снабжен условной компиляцией `#ifdef _WIN32`. На целевых серверах продакшена под управлением **Linux (Docker/Kubernetes)** данные вызовы изолируются, так как ядро Linux «из коробки» использует механизм **`hrtimers` (High-Resolution Timers)**, гарантируя аппаратную микросекундную точность обработки дедлайнов (выполнение ровно в **500–501 мс**).

## 🚀 Как запустить проект

1. Убедитесь, что зависимости `gtest`, `protobuf` и `gRPC` настроены в вашей системе.
2. Откройте проект в Visual Studio как CMake-директорию.
3. Дождитесь автоматической генерации C++ файлов из `service.proto` утилитой `protoc` (настроено через инкрементальный `add_custom_command` в `CMakeLists.txt`).
4. Откройте **Обозреватель тестов (Test Explorer)**. Нажмите запуск для целей `grpc_memory_tests` или `grpc_cpu_tests`.
